## Q1. 计算节点在项目里到底是什么？在什么上面实现的？

**计算节点有两层含义：**

**① 物理层：一台能跑 Docker 的机器**——服务器、工作站、云主机均可，唯一硬要求是装了 Docker，上面跑一个 Agent 进程。

**② 平台层：`compute_node` 表的一行**——resource 服务维护的调度对象。该表**不启用 RLS**（`V600002` 注释："平台共享表，调度器需全局可见所有节点"），因为调度要跨租户看到全部可用节点。

**表字段（`V600002__create_compute_node_table.sql`）**

| 字段 | 说明 |
|---|---|
| `agent_id` | Agent 唯一标识（唯一约束） |
| `node_name` / `ip_address` | 节点名 / IP |
| `status` | online / offline / maintenance |
| `cpu_info` / `gpu_info` | JSONB；GPU 为数组 `[{index,model,memoryMb,cudaVersion}]` |
| `total_memory` / `total_disk` | 字节 |
| `labels` | JSONB，如 `{region, gpu_type}`，供调度筛选 |
| `last_heartbeat_at` | 心跳时间 |
| `running_tasks` | 当前运行任务数（V600005 增加） |

**实现形态**

Agent 本体是 Go 1.24 编译的二进制（`docker/agent/Dockerfile` 内 `go build -o /agent .`），**以 Docker 容器形式部署**在节点上。关键在 `deploy/docker-compose.yml:235-239` 的两个挂载：

```yaml
volumes:
  - /var/run/docker.sock:/var/run/docker.sock
  - /tmp/aisys-agent:/tmp/aisys-agent
```

- **`docker.sock` → 兄弟容器模式**：Agent 容器内调 `docker run`，请求经 socket 到宿主 Docker daemon，由宿主拉起模型容器。模型容器是 Agent 容器的**兄弟**而非嵌套（非 Docker-in-Docker）。资源配额、隔离、日志采集全用 Docker 原生能力。
- **`/tmp/aisys-agent` 共享 → 挂载路径可解析**：Agent 建 `/tmp/aisys-agent/aisys-task-<id>/{dataset,output}` 后 `-v` 挂给模型容器。路径必须在宿主存在且共享，宿主 docker daemon 才能解析；不共享则挂载成空目录，模型读不到数据集、写不出 output（compose 注释已注明，路径须与 `AISYS_WORK_DIR` 默认值一致）。

**注册与链路位置**

```
节点机器（装 Docker）
  └─ Agent 容器（Go 二进制，挂 docker.sock + 工作目录）
       │ 启动带 AGENT_ID / NODE_NAME / ENROLL_TOKEN
       ↓ 注册 + WS 长连接
  resource 服务
       ├─ compute_node 表 upsert 一行（agentId + 硬件信息 + online + 心跳）
       └─ 调度器消费 MQ task.command
            → 从表挑 online 节点（按 labels / gpu 筛）
            → 预签名 S3 URL
            → WS run_task 发给该节点 Agent
                 ↓ 宿主 docker daemon 拉起模型容器
```

**代价与安全边界**：Agent 容器挂了 `docker.sock`，等价于宿主 root 权限（可拉起任意容器），因此只应部署在可信专用节点。平台的沙箱隔离隔离的是**被测模型容器**，不是 Agent 自身。单机 compose 部署主要用于功能验证；生产上 Agent 应部署到独立计算节点，`PLATFORM_ADDR` 指向 resource 服务即可横向扩容。

## Q2. 相当于它的作用就是拉起容器，所以一个服务器一个 agent？

**部署模型正确**：一台服务器 = 一个 Agent = `compute_node` 表里一行（`agent_id` 唯一约束保证 1:1）。

**但"作用就是拉起容器"略窄**——拉起容器是核心动作，实际承担的是「任务在该节点上的完整生命周期」+「让机器被看见、被调度、被观测」：

```
注册登记   → 上报 CPU/GPU/内存/磁盘，让平台知道机器能力
心跳保活   → online / offline 状态维护
接收任务   → WS 收 run_task
准备数据   → 预签名下载数据集、自动解压、选挂载策略
拉起容器   → docker load + docker run（核心动作）
实时采集   → stdout 逐行清洗 + JSONL 帧解析
实时回传   → status / log / metrics 经 WS 发回平台
上传产物   → best.pt PUT 到对象存储
终态上报   → result 帧
```

**关键点**：平台从不直接碰计算节点——resource 服务对节点的所有操作都经 Agent 的 WebSocket 长连接。因此

> Agent 挂了 = 节点 offline，即使 Docker 本身正常，这台机器也接不到任何任务。

反之，Agent 在但 Docker daemon 挂了，节点仍显示 online，任务会执行失败。

**更准确的定位**：Agent 是**计算节点在平台里的"代理人"**——拉起容器是核心动作，同时负责让这台机器被看见（注册/硬件上报）、被调度（状态/心跳/运行任务数）、被观测（实时日志指标回传）。

技术上也可在一台机器跑多个 Agent（不同 `AGENT_ID` 即不同节点），但无实际意义。

## Q3. 与 Agent 的通信是怎么实现的？

分两段：**一次 HTTP 注册 + 一条 WebSocket 长连接**，之后所有指令与数据都走这条长连接。

**① 注册（HTTP，一次性）**

`agent.go:31-62` `register(cfg)`：`POST http://{PLATFORM_ADDR}/api/v1/agent/register`，带 enrollment token → 返回 `agentId` + `agentToken`。token 存内存，后续通信不再走 URL 传参。

**② 长连接（WebSocket）**

```go
dialer := websocket.Dialer{HandshakeTimeout: 10 * time.Second}  // agent.go:115
```
连到 `resource:8006/ws/v1/agent/connect`（gateway 路由）。resource 侧 `WebSocketConfig.java:28` 注册该端点，`setAllowedOriginPatterns("*")`。

**③ 鉴权（首帧）**

连接建立后**第一条文本消息必须是 auth 帧**（`messages.go:8-13`）：
```json
{"type":"auth","agentId":"agent-sim-01","data":{"agentToken":"..."}}
```
`AgentWebSocketHandler.java:104-112`：校验 **Redis 中 `agent:token:{agentId}` == agentToken；通过前不处理任何其它消息**，失败直接关 session。设计意图：**token 不走 URL**（避免出现在 URL/日志中）。

**④ 下行：平台 → Agent（Command）**

`messages.go:22-36`，`Type` 为 `run_task` / `stop_task` / `pause_task` / `update_agent`；字段含 `taskId`/`taskType`(TRAINING/EVALUATION)/`tenantId`/`traceId`/`image`/`command`/`args`/`env`/`gpuDevices`/`cpu`/`memoryBytes`/`outputDir`/`version`。Agent 收 `run_task`（`agent.go:159`）→ 起 goroutine 执行。

**⑤ 上行：Agent → 平台（Report）**

`messages.go:51-59`：
```go
type Report struct {
    Type     string         // status / log / metrics / result
    TaskID   int64
    TaskType string
    Level    string         // log: INFO/WARN/ERROR
    Message  string         // log/status 文本
    Metrics  map[string]any // metrics 帧
    Data     map[string]any // status:{status,progress} / result:{...}
}
```
resource 侧 `handleTextMessage`（`AgentWebSocketHandler.java:69`）按 type 分发 → `forwardStatus`/`forwardLog`/`forwardMetrics` → MQ → training/evaluation 落库。

**Report 结构与 resource 侧 `WebSocketMessage.java` 字段对齐**——改任一侧都要同步。

**⑥ 可靠性设计**

| 机制 | 实现 |
|---|---|
| 心跳 | `messages.go:18` `type:"ping"` 保活；`last_heartbeat_at` 写 compute_node 表 |
| 重连 | 断开后指数退避重连 + 重新注册（`agent.go:103`） |
| 消息上限 | WS 文本缓冲 **64KB**（`WebSocketConfig` 的 `ServletServerContainerFactoryBean`，默认 8KB 太小） |
| 日志帧瘦身 | log 帧**不带 `Data`**，只带 `Level`+`Message`，避免长 message 触发 `close 1009` 致检查点丢失（metric 帧小才带 Data） |
| 异常关闭识别 | `agent.go:141` `websocket.IsCloseError(err, ClosePolicyViolation)` 识别消息超限关闭 |

**完整流向**

```
启动 register(HTTP) → 拿 agentId + agentToken
        ↓
WS 连接 → 首帧 auth 鉴权（Redis 校验）
        ↓
   ┌──────────── 长连接双向 ────────────┐
   ↓ Command                    Report ↑
run_task / stop_task     status / log / metrics / result
                                  ↓
                     resource 按 type 分发 → MQ
                                  ↓
                  training / evaluation 落库 → 前端
   └──────────────────────────────────────┘
```

## Q4. 上行 Report 是只有训练模式采用吗？

**不是。Report 是训练与评测共用的**——Agent 不区分任务类型，只管跑容器、解析 stdout、按帧类型转发。

**区分靠 `TaskType` 字段，不是两套协议**

`ForwardServiceImpl` 用 `msg.taskType()` 拼路由键：

```java
// ForwardServiceImpl.java:70 / :203 / :222
publish(m, EXCHANGE_TASK_STATUS,  "task.status."  + lower(msg.taskType()), ...);
publish(m, EXCHANGE_TASK_LOG,     "task.log."     + lower(msg.taskType()), ...);
publish(m, EXCHANGE_TASK_METRICS, "task.metrics." + lower(msg.taskType()), ...);
```

| | 训练 | 评测 |
|---|---|---|
| 消费者 | training 服务 | evaluation 服务 |
| 状态消费 | `handleStatusEvent` → 更新任务 + 写 checkpoint | `handleSubtaskStatus` → 更新子任务 + 写 `evaluation_result` + 聚合父任务 + 触发 LLM 报告 |
| 日志 | → `task_log` 表 | → `task_log` 表（同表） |
| 指标 | → `task_metric` 表（JSONB，15s 降采样） | → `task_metric` 表（同表） |

`forwardResult`（`:228-230`）内部调 `forwardStatus`——**result 帧走 status 通道**。

**真正差异在"容器 emit 了什么"，不在协议**

| | 训练 | 评测 |
|---|---|---|
| `metric` 帧 | **多**（每 epoch 一次，画损失曲线） | **少甚至没有**（评测是一次性推理，非 epoch 迭代） |
| `result` 帧载荷 | `weights` 路径 → checkpoint 下载 | `overall_scores` / `category_scores` → 评测分数 + LLM 报告 |

这解释了评测报告里 `metricKeys` 只有 `confusion_matrix` 的现象——评测容器的 `run.py` 把指标全塞在 `result` 里，没按 step emit `metric` 帧。平台"容器 emit 什么就收什么"。要评测也有逐步曲线，需改评测容器 `run.py` 的 `evaluate()` 按进度 emit `metric` 帧（同训练侧 `on_fit_epoch_end` 回调写法）。

## Q5. 项目中 Nacos 和 Spring Cloud 支撑什么功能？

### Spring Cloud（微服务框架工具集）

本项目用 **Spring Cloud 2025.1.2 + Spring Cloud Alibaba 2025.1.0.0**。它把"一堆独立 Spring Boot 服务"变成"可互相发现、互相调用的分布式系统"。在本项目确认启用的能力：

| 能力 | 组件 | 本项目落地 |
|---|---|---|
| **服务注册与发现** | Spring Cloud Alibaba Nacos Discovery | 各服务启动即注册，按服务名互调 |
| **声明式服务调用** | Spring Cloud OpenFeign | `@FeignClient(name="aisys-model")` 等服务名直调，无硬编码 IP |
| **API 网关** | Spring Cloud Gateway | `RouteConfig.java` 路由 `/api/v1/<domain>/**` 到对应服务 |
| **客户端负载均衡** | Spring Cloud LoadBalancer | Feign / Gateway 按服务名解析出多实例时选一个 |

**实际代码证据**：
```java
@FeignClient(name = "aisys-model",   contextId = "evalModelClient")     // evaluation 调 model
@FeignClient(name = "aisys-dataset", contextId = "evalDatasetClient")   // evaluation 调 dataset
@FeignClient(name = "aisys-resource",contextId = "resourceClient")
```
评测服务拿模型/数据集元数据，就靠这两个 Feign 接口——**只写服务名，不写 IP:端口**。

### Nacos（注册中心 / 配置中心）

Nacos 是阿里开源的动态服务发现、配置管理和服务管理平台。容器部署为 `nacos/nacos-server:v3.2.2`，端口 **8848**。

**本项目只用了它的「服务注册与发现」能力**（配置中心未启用——`application.yml` 里只有 `spring.cloud.nacos.discovery`，无 `spring.cloud.nacos.config`；配置来自 `application.yml` + 环境变量）：

```yaml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: ${NACOS_ADDR:nacos:8848}
        namespace: ${NACOS_NAMESPACE:public}
        register-enabled: ${NACOS_REGISTER:true}
```

Nacos 承担的具体职责：
1. **服务注册表**：维护 `服务名 → 实例列表(IP:Port)`。10 个后端服务 + gateway 全部注册。
2. **健康检查 / 心跳**：实例定期心跳，宕机实例从注册表摘除，调用方不再路由到它。
3. **服务名解析**：Feign / Gateway 用服务名查 Nacos 拿真实地址。

### 二者如何配合

```
启动：各服务 → 向 Nacos 注册自己（服务名 + IP:Port）
调用：evaluation 的 @FeignClient("aisys-model")
        → Spring Cloud LoadBalancer 问 Nacos："aisys-model 有哪些实例？"
        → Nacos 返回实例列表
        → 选一个 → HTTP 调用
入口：外部请求 → Gateway → 按 path 前缀映射到服务名 → 查 Nacos → 转发
```

### 没有它们会怎样

- 服务间调用要**硬编码 IP:端口**，扩容/迁移/换机器就得改代码重启。
- Gateway 无法按服务名路由，只能写死后端地址。
- 实例宕机无法自动摘除，请求会打到死节点。

**一句话**：Spring Cloud 是"微服务该怎么组织"的框架（提供网关、Feign、负载均衡等标准件），Nacos 是"服务在哪里"的通讯录（注册中心）。本项目里 Spring Cloud 负责调用与路由的**机制**，Nacos 提供**地址**。

## Q6. 有点像 nginx？

直觉很准——**项目里真的用了 nginx，在前端那一层**。`docker/web/Dockerfile` 首行注释：

```
# 前端：node 构建 vue-pure-admin dist，nginx 托管并反向代理 /api、/ws 到网关
```

**是两层代理，各司其职**：

```
浏览器 → nginx（web 容器 :80，映射宿主 8081）
           ├─ /        → 静态 dist（Vue 页面）
           ├─ /api/**  → proxy_pass → gateway:8080
           └─ /ws/**   → proxy_pass → gateway:8080（含 WebSocket 升级）
                              ↓
                      Spring Cloud Gateway
                              ↓ 按 path 前缀 → 服务名
                      Nacos 解析服务名 → 实例 IP:Port
                              ↓
              各微服务（training / evaluation / resource ...）
```

`docker/web/Dockerfile` 基于 `nginx:1.27-alpine`，`COPY --from=build /app/dist /usr/share/nginx/html`。

**nginx vs Spring Cloud Gateway + Nacos**

| | nginx | Spring Cloud Gateway + Nacos |
|---|---|---|
| 配置方式 | 静态文件 nginx.conf | 代码/配置 + 运行时注册 |
| 后端地址 | 手写 `upstream {server ip:port;}` | Nacos 动态维护实例表 |
| 实例变化 | 改配置 + reload/重启 | 自动感知（心跳注册/宕机摘除） |
| 路由规则 | `location` 前缀/正则匹配 | Predicate（path/header/method…）+ Filter 链 |
| 擅长 | 静态资源托管、TLS 终止、边界反代、限流 | 微服务内部治理、动态伸缩、按服务名调用 |
| 服务间互调 | 无（要硬编码 URL 或再走 nginx） | Feign 声明式，按服务名直调 |

**核心差别一句话**：nginx 的 upstream 是**写死在配置里的**；Nacos 的实例表是**服务自己注册上来的、会动态变的**。微服务场景里实例频繁上下线，靠手改 nginx.conf 不现实，所以用注册中心。

**本项目为什么不只用 nginx 反代后端**：
- 10 个服务 + 多实例，手写 upstream 维护成本高、扩容要改配置重启。
- 服务之间还要互相调用（evaluation 调 model/dataset），nginx 解决不了，需要 Feign + 服务名解析。
- 需要实例级健康检查与自动摘除。

**反过来，为什么边缘还留着 nginx**：托管 Vue 静态资源（dist）是 nginx 的强项，顺手把 `/api`、`/ws` 反代到网关，浏览器只暴露 8081 一个端口。二者是**互补而非替代**关系。

## Q7. 拉起 Docker 容器沙箱时，项目里有什么资源划分规则？

有完整规则，是**"调度侧配额预留 + 执行侧 Docker 硬限制"两层**。

### 数据模型（三张表/实体）

| 实体 | 作用 |
|---|---|
| `NodeGroup` | 节点分组（id/name/description），`compute_node.node_group_id` 引用它 |
| `ComputeNode` | 节点能力账本：`cpu_info`、`gpu_info`（数组含型号/显存/CUDA）、`total_memory`、`total_disk`、`labels`（JSONB，如 `{region, gpu_type}`）、`running_tasks` |
| **`ResourceAllocation`** | **资源租约**：`nodeId`/`taskType`/`taskId`/`tenantId`/`gpuCount`/`cpu`/`memoryBytes`/`gpuDevices`/`status`/`acquiredAt`/`releasedAt` |

### 调度侧（`SchedulingServiceImpl`，DDD 5.7.3）

```
1. selectOnlineCandidates()            ← 取所有 online 节点               (:154)
2. sumHeldByNodes(nodeIds)             ← 聚合各节点已被占用的资源         (:162)
3. freeCapacity(node, held)            ← 算每个节点的空闲量               (:169)
4. labelMatches(node, taskSpec)        ← 标签过滤（区域 / GPU 型号等）     (:171)
5. 资源量 + 标签预过滤 → 候选 ScoredNode 列表
   └─ 无节点满足则记日志"无节点满足资源需求"并拒绝                     (:175-176)
6. strategy.schedule(spec, candidates) ← BestFitStrategy 选最优节点       (:181)
7. 在 lock:node:{nodeId} 分布式锁内：
   double-check 空闲量 → 写 resource_allocation(held) → WS 下发 run_task  (:184)
```

关键点：
- `NodeHeldAggregate` 聚合每节点已"持有"的分配，`总量 - 已持有 = 空闲` 判断能否放下新任务。
- **分布式锁 + double-check**（注释明确防"Agent 已在跑但租约被回滚 → GPU 被二次分配"这类竞态）。
- **策略可插拔**：`SchedulingStrategy` 接口 + `BestFitStrategy` 实现（最佳适配，挑剩余资源最贴合的节点，减少碎片）。
- 选不中直接拒绝并记日志，不超卖。

### 执行侧（Agent，`executor.go:172-184`）

```go
// 资源限制：CPU / 内存始终生效；GPU 仅在分配了设备时透传（CPU 节点不传 --gpus，避免 docker 报错）
if cmd.CPU > 0    { args = append(args, "--cpus", strconv.Itoa(cmd.CPU)) }
if cmd.Memory > 0 { args = append(args, "--memory", strconv.FormatInt(cmd.Memory, 10)) }
if len(cmd.GPUDevs) > 0 { args = append(args, "--gpus", `"device=0,1"`) }
```

### 其他隔离维度

| 维度 | 规则 |
|---|---|
| 文件系统 | 只挂 `dataset`（按结构 ro/rw）+ `output`，不给平台目录 |
| 网络 | 默认关闭外网，仅授权开放指定地址 |
| 运行时间 | 任务级超时控制 |
| 生命周期 | `--rm` 退出即删；工作目录 `/tmp/aisys-agent/aisys-task-<id>/` 用 `defer os.RemoveAll` 清理 |
| 节点离线 | `NodeOfflineScheduler` 定期把心跳超时节点标 offline，不再参与调度 |

**一句话**：调度层记账（租约 + 空闲量 + 分布式锁防超卖 + BestFit 选点），执行层硬限（Agent 把配额翻译成 `--cpus`/`--memory`/`--gpus` 交给 Docker cgroups 强制生效）。

## Q8. 用了哪些技术栈支撑？

### A. 支撑「容器沙箱 + 资源划分」这块

| 技术 | 承担角色 |
|---|---|
| **Docker Engine** | 沙箱本体。`--rm` 生命周期、`-v` 挂载隔离、`--network` 网络隔离 |

## Q9. 如何使用 Redis 和 RabbitMQ 实现功能？

### 一、Redis（`StringRedisTemplate`，四类用途）

**① Agent Token 鉴权** —— `agent:token:{agentId}` = agentToken

- 注册时写入（`AgentServiceImpl`：先 `get` 查已有（:103），再 `set(key, token, AGENT_TOKEN_TTL)`（:107））
- WS 首帧鉴权时读取比对（`:162`：`redis.opsForValue().get(REDIS_KEY_AGENT_TOKEN_PREFIX + agentId)`）
- **为什么必须放 Redis**：resource 服务若多实例部署，WS 连接可能落在与注册时不同的实例上，本地内存不共享；token 必须集中存放才能跨实例校验。

**② 分布式锁（调度防超卖）** —— `lock:node:{nodeId}`

- `DistributedLock`（`aisys-common-redis/lock`）：**`SET NX EX` 获取 + Lua 脚本（校验 token）释放 + 看门狗按租约 1/3 周期续期**
- 调度时使用（`SchedulingServiceImpl`）：
  ```java
  String token = distributedLock.tryLock(lockKey, Duration.ofSeconds(leaseSeconds + 10));  // :186
  //   锁内：double-check 空闲量 → 写 resource_allocation(held) → WS 下发 run_task
  distributedLock.unlock(lockKey, token);                                                   // :194
  ```
- **防的竞态**（注释原文）："Agent 已在跑但租约被回滚 → GPU 被二次分配"。即并发调度时两个任务同时判定同一块 GPU 空闲，导致重复分配。锁 + 锁内二次校验解决。
- 用 token 而非直接 DEL：确保只释放自己持有的锁，避免误删他人锁（看门狗续期期间不会失效）。

**③ 节点状态缓存** —— `node:status:{nodeId}` = online

- 写入带 TTL（`:177`：`set(key, status, Duration.ofSeconds(nodeStatusTtlSeconds))`）或不带 TTL（`:179`）

**④ 任务上下文映射** —— `taskCtxKey(taskType, dispatchId)`

- `:138` `redis.opsForValue().set(taskCtxKey(...), ...)`——记录 `dispatchId ↔ taskId` 映射，供 Agent 状态回传时反查归属任务（评测时 `dispatchId == subtaskId`，训练时 `== taskId`）。

### 二、RabbitMQ（四个 topic 交换器 + Outbox 模式）

**交换器**（`CommonConstants:31-34`）

| 交换器 | 方向 | 用途 |
|---|---|---|
| `task.command` | 平台 → 调度 | 下发训练/评测指令 |
| `task.status` | Agent → 平台 | 任务状态 + 终态帧 |
| `task.log` | Agent → 平台 | 运行日志 |
| `task.metrics` | Agent → 平台 | 每轮指标 |

**Outbox 模式（保证 DB 与 MQ 一致性）**

```
业务方法（@Transactional 内）
  → EventPublisher.publish(msg, exchange, routingKey, aggregateType, aggregateId)
  → 仅写本地 event_outbox 表（status=pending），与业务操作同一事务   ← EventPublisher.java:35-39
        ↓（事务提交后，异步）
OutboxPublisher @Scheduled(fixedDelayString = "${aisys.outbox.poll-interval-ms:3000}")
  → 每 3 秒轮询，selectPendingForUpdate(producer, 100) 一次取 100 条（FOR UPDATE 行锁防重复投递）
  → requiresNewTx（独立新事务）投递到 RabbitMQ
  → 成功则更新 outbox 状态                                          ← OutboxPublisher.java:48-61
```

**意义**：避免"DB 提交成功但 MQ 发送失败"（任务状态已改但没人执行）或反之（指令发了但状态没改）的不一致，**不引入分布式事务**（无 2PC、无 TCC 复杂度）。

**路由键设计**

- 命令侧按 taskId 细分：`task.command.train.{taskId}` / `task.command.eval.{id}`
- 状态侧按 taskType 拼接（`ForwardServiceImpl:70/:203/:222`）：
  ```java
  "task.status." + lower(msg.taskType())   // → task.status.training / task.status.evaluation
  "task.log."    + lower(msg.taskType())
  "task.metrics."+ lower(msg.taskType())
  ```

**消费端绑定**（training 为例）

```java
// TrainingMqConfig.java:36
BindingBuilder.bind(taskStatusQueue).to(taskStatusExchange).with("task.status.training");

// TaskEventConsumer.java
@RabbitListener(queues = TrainingMqConfig.QUEUE_STATUS)    // :41 → handleStatusEvent
@RabbitListener(queues = TrainingMqConfig.QUEUE_LOG)       // :58 → onLog（写 task_log）
@RabbitListener(queues = TrainingMqConfig.QUEUE_METRICS)   // :75 → onMetrics（写 task_metric）
```
evaluation 侧同样绑 `task.status.evaluation` → `handleSubtaskStatus`。

**完整链路（训练为例）**

```
training POST /tasks/{id}/start
  → EventPublisher 写 event_outbox(pending)【与业务同事务】
  → OutboxPublisher 3s 轮询 → 投递 RabbitMQ（task.command.train.{id}）
  → resource TaskCommandConsumer 消费
  → SchedulingServiceImpl：选节点（Redis 锁 + BestFit）→ 预签名 S3 → WS run_task → Agent
  → Agent 跑 Docker 容器 → stdout JSONL
  → Agent WS Report(status/log/metrics/result)
  → resource forwardStatus/Log/Metrics → publish 到 task.{status,log,metrics}.training
  → training TaskEventConsumer @RabbitListener 消费
  → handleStatusEvent（更新任务/写 checkpoint）/ onLog（task_log）/ onMetrics（task_metric）
  → 前端 3s 轮询展示
```

**为什么用 MQ 而非直接 HTTP 调用**：解耦服务（training 不认识 resource）、削峰（任务突发时排队）、可靠（消息持久化 + 消费确认）、广播（一条状态可同时被多个消费者订阅）。
