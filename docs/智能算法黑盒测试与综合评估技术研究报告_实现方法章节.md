# 第五章补充 本项目实现方法

前述各章阐述了智能算法黑盒测试与综合评估的技术路线与实施方案。为验证该路线的工程可行性，本研究构建了平台原型系统 aisys，并已实现"算法接入—容器化执行—数据采集—综合评测—报告生成"的全链路闭环。本章阐述该平台的核心实现方法，重点说明容器化执行环境、Agent 工作流管理、评测报告动态生成三项关键机制的工程实现，以及在实现过程中所解决的关键工程问题。

## 5.A 实现概述

本平台采用微服务架构，由网关、认证、模型管理、数据集管理、训练、评测、资源调度、对象存储、通知、审计十个后端服务，一个 Go 语言实现的 Agent，以及 Vue 3 前端构成。后端基于 Spring Boot 4.1 与 Spring Cloud 2025.1.2 框架，以 Nacos 进行服务注册与发现，以 RabbitMQ 实现事件驱动通信，以 PostgreSQL（行级安全策略实现多租户隔离）和 SeaweedFS（S3 兼容对象存储）进行数据与文件持久化。全部服务以容器形式编排部署。

平台遵循"每个模型即为一个容器"的工程契约：被测算法以 Docker 镜像 tar 形式交付，由调度服务预签名对象存储访问地址后下发至计算节点，Agent 拉取并加载镜像，以标准化的挂载方式与环境变量启动容器，容器入口脚本按统一协议向标准输出流输出结构化数据，由 Agent 解析并实时回传。该契约使来源于不同框架、不同依赖、不同程序设计语言的异构算法能够在统一的输入输出条件下接受公平测试，且算法研制单位无需暴露源代码即可完成第三方交付。

## 5.B 容器化执行环境与模型接入契约

### 5.B.1 模型容器化封装

模型版本以镜像 tar 形式存储于对象存储。模型管理服务支持分片直传与基于校验和的秒传去重，tar 文件落盘后回写相对存储路径与配置信息（含镜像标签、框架、任务类型等）。调度阶段，资源调度服务依据模型版本信息生成预签名下载地址，连同预签名上传地址一并通过任务指令下发至 Agent，使 Agent 在执行前后均具备对象存储的受控访问能力，避免长次凭证泄露。

### 5.B.2 标准化输入输出协议

为消除异构算法输出格式差异对评测流水线的影响，平台定义了基于 JSON Lines 的标准输出协议。容器入口脚本向标准输出逐行输出四类帧：

- **状态帧**（`status`）：报告任务运行状态与进度，供平台更新任务进度。
- **日志帧**（`log`）：报告运行日志，含等级与消息，供平台落库与前端实时展示。
- **指标帧**（`metric`）：报告每轮（epoch/批次）量化指标，含步数、进度与指标键值对，供平台绘制训练曲线。
- **终态帧**（`result`）：任务结束时输出恰好一次，携带最终指标与产物路径。

该协议将黑盒算法的"能运行"转化为"可计算"：Agent 仅依据协议解析输出，无需理解算法内部实现，即可将异构输出转化为统一元数据进入后续数学评估模型。

### 5.B.3 沙箱隔离与资源管控

Agent 依托容器标准能力实现被测算法的隔离执行。文件系统层面，仅向容器挂载输入目录（只读）、输出目录（可写）与只读模型目录，禁止其访问平台控制目录与其他任务数据；网络层面，默认关闭外部访问，仅在授权情况下开放指定地址，以规避算法在运行过程中因联网下载依赖（如字体文件、预训练权重）而导致的执行卡滞与不可复现问题；资源层面，对处理器、图形处理器、内存、显存与运行时间均设置配额上限，避免异常算法造成资源失控。对已交付镜像，平台执行签名校验与基础漏洞扫描；对仅提供压缩包的算法，平台依据依赖说明生成临时构建脚本完成封装。

### 5.B.4 镜像缓存与版本治理

为避免每次任务重复拉取与加载大体积镜像 tar，Agent 依据镜像标签对已加载镜像进行本地缓存，命中即跳过下载加载环节。该优化带来一个需要严格约束的副作用：当模型容器内容（入口脚本、依赖、Dockerfile）发生变更并重新打包时，必须采用新的版本标签而非复用既有标签，否则 Agent 将继续使用本地缓存的旧镜像，导致新代码无法生效。平台模型版本的镜像标签须与实际打包标签保持一致，以维持可追溯性。

## 5.C Agent 工作流与实时数据采集

### 5.C.1 注册与长连接

Agent 部署于计算节点，启动后向资源调度服务发起注册，获得鉴权令牌后建立至资源服务的 WebSocket 长连接。鉴权采用首帧令牌机制，连接建立后首帧携带令牌，校验通过前不接受其余消息。连接中断时，Agent 依据指数退避策略自动重连并重新注册，资源服务侧维护 Agent 与计算节点的映射关系并实施心跳保活。

### 5.C.2 任务调度与执行

Agent 收到 `run_task` 指令后，在独立执行单元中完成下述流程：首先依据镜像标签判断本地缓存，命中则跳过加载，否则拉取 tar 并执行 `docker load`，并以加载后解析得到的实际标签修正镜像名，以兼容 tar 内部标签与配置标签不一致的情形；其次建立任务工作目录，依据预签名地址下载并按需解压数据集，依据数据集目录结构（三分割或扁平）选择挂载策略；继而构造容器运行参数，以标准化挂载与环境变量启动容器；最后在容器运行期间实时解析其标准输出。任务工作目录在任务结束时由延迟清理机制移除，避免存储累积。

### 5.C.3 标准输出流解析与实时回传

Agent 以行缓冲方式读取容器标准输出，对每一行依次执行清洗与解析：先剥离 ANSI 转义序列与控制字符，对包含多个回车符的行取其末段（即最新进度状态），并按字符长度截断至上限以内，以避免单条回传消息触发通信边界异常；继而依据 JSON 协议解析帧类型，按状态、日志、指标、终态分别构造回传消息，经 WebSocket 实时发送至资源服务。资源服务依据消息类型分发至状态、日志、指标三类转发器，分别经消息队列发布至对应主题，由训练或评测服务消费落库。该机制使前端监控页能够在算法运行期间实时滚动展示日志与指标曲线，而非等待任务结束方获得结果，显著提升了测评过程的可观测性。

需要指出，容器运行时不分配伪终端，并显式禁用进度条库的交互式刷新，以避免进度条以回车符原地刷新所导致的行累积——该情形会使单行长度突破扫描缓冲上限并触发静默退出，从而使后续输出全部丢失。

### 5.C.4 训练产物上传与终态上报

容器退出后，Agent 扫描输出目录，依据权重文件扩展名与命名优先级选取最佳权重，按预签名上传地址以 HTTP PUT 方式上传至对象存储。上传成功后，Agent 发出携带存储路径的第二次状态上报；同时，容器退出时发出的终态帧亦携带容器声明的权重路径。平台在状态转发层对两条上报均进行存储路径提取与冗余去重，使检查点的写入具备幂等性，即便其中一条上报丢失，另一条仍可完成检查点记录。

## 5.D 评测报告动态生成机制

本平台将评测报告生成从静态模板填充升级为基于大语言模型的数据驱动生成，使报告能够依据实际评测数据与任务类型动态组织内容，并提出可执行的改进建议。该机制的工程实现核心在于上下文数据装配与任务类型感知的提示词构造。

### 5.D.1 上下文数据装配

报告生成器在生成前，从数据库收集全量上下文数据，包括：任务基本信息、全部被测模型的评测结果（总体指标与分类指标的 JSONB 自由结构）、基准测评集配置、各子任务的错误信息、任务超参，以及经服务间调用获取的模型元数据（名称、描述、任务类型）与数据集元数据（名称、描述、任务类型、样本规模）。

其中，模型与数据集的元数据获取经历了关键改造。原始实现中，版本查询接口仅返回版本表自身字段，未关联父表，导致报告生成时模型名称与描述恒为占位符。为此，平台在模型版本查询中联表查询模型主表，在数据集版本查询中联表查询数据集主表，使版本接口一次调用即可返回父表元数据，消除了报告生成阶段的信息断点。

特别地，指标清单的确定采用数据驱动策略：不预设指标名称白名单，而是遍历全部评测结果的总体指标与分类指标 JSONB 字段，收集其顶层键名作为本次评测的产出指标清单。该策略使平台无须针对不同算法类型维护指标枚举，无论是计算机视觉检测任务的 mAP、分类任务的准确率，还是时序预测任务的 MAE 与趋势准确率，均能被自动识别并纳入报告。

### 5.D.2 任务类型感知的提示词构造

系统提示词采用通用骨架与任务类型分支相结合的设计。通用骨架规定了报告的统一结构、风格约束与建议机制：风格上禁止营销化措辞，要求每个结论引用具体数值，对样本不足的情形显式标注待验证状态，禁止臆测未提供的原因；结构上包含评测概况、核心指标解读、类别级分析、弱项与风险、改进建议、结论与部署建议六个章节；其中弱项与风险章节采用"问题描述—证据—量化影响—可能原因—改进建议"的链式结构，并按漏检、误检、类别混淆、定位偏差、置信度异常、输出协议异常六类失效模式进行分类；改进建议章节要求按"立即可做、需返工、需重训练"三档给出，每条建议须绑定具体指标与可量化的预期收益；结论章节须依据红线判定给出推荐、受限推荐或不推荐的明确意见。

任务类型分支仅作用于核心指标解读章节的举例说明：对目标检测任务列举 mAP 与分尺度精度，对图像分类任务列举准确率与混淆矩阵，对时序预测任务列举误差与趋势指标，对未识别类型则不举具体例子而依指标清单逐项解读。基准测评集若配置了自定义提示词模板，则作为风格补充附加至系统提示词末尾，使测评集配置者能够按需定制报告取向。

### 5.D.3 大语言模型调用与配置

平台以 JDK 原生 HTTP 客户端调用大语言模型，依据服务地址自动适配 Ollama 原生格式或 OpenAI 兼容格式。生成温度设为较低值以保障严肃报告的稳定性，输出长度上限适度放宽以容纳多模型多章节内容。模型服务地址、密钥、模型名与超时参数均经环境变量注入，且环境变量以独立配置文件形式管理，与容器编排文件解耦，使配置变更无须重新编译构建，仅需重建容器即可生效。

### 5.D.4 报告存储与回显

生成的报告以 Markdown 与 HTML 双格式持久化至评测报告表，记录所用模型、提示词摘要与生成状态。前端在报告生成阶段以固定间隔轮询状态，生成完成后渲染 Markdown 正文并叠加评测数据概览。平台支持强制重新生成与多格式导出。

## 5.E 关键工程问题与解决方案

在实现过程中，本研究解决了若干具有普遍意义的工程问题：

**输出流累积溢出。** 进度条库在感知到交互式终端时会以回车符原地刷新进度，而行扫描器仅以换行符分割，二者结合会导致单行长度持续累积并突破缓冲上限，触发静默退出，使后续日志、指标与终态帧全部丢失。本研究通过不分配伪终端、显式禁用进度条交互、扩大扫描缓冲、对包含回车符的行取其末段并截断、以及在扫描退出后检查并记录错误等多重措施，根本性消除了该失效路径。

**通信消息边界。** WebSocket 文本消息默认缓冲上限较小，超长日志帧会触发连接关闭异常，导致后续状态帧丢失，表现为任务完成但检查点未写入。本研究通过提升缓冲上限、对日志类回传消息仅携带必要字段而摒弃原始数据对象、以及对回传文本实施长度截断，消除了该异常。

**元数据获取断点。** 跨服务调用未返回父表信息，导致报告关键元数据缺失。本研究在不变更数据库模式的前提下，通过联表查询与数据传输对象字段扩展，使元数据随版本查询一并返回，消除了报告生成的信息盲区。

**配置热加载。** 模型服务配置原与构建产物耦合，变更需重新编译。本研究将可变配置外置为环境变量与独立配置文件，并经由容器编排注入，使配置层与代码层解耦，配置变更仅需重建容器而无须重新构建镜像。

## 5.F 小结

本章阐述了平台原型系统在容器化执行、Agent 工作流、评测报告动态生成三方面的实现方法。该实现验证了前述理论研究路线的工程可行性：黑盒算法能够以容器为边界接受标准化测试，运行过程数据能够被实时采集与持久化，评测报告能够依据实际数据与任务类型动态生成且包含可执行的改进建议。实现过程中所解决的输出流溢出、通信边界、元数据获取与配置热加载等问题，对同类智能算法测试平台的工程实现具有参考价值。
